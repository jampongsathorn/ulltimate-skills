# Goal Keeper — กันหลงทางจาก Big Goal

## ทำไมต้องมี skill นี้
เมื่อ agent ทำงานแบบ "ทำ small task ทีละอันจนกว่าจะถึง goal" เป้าหมายเดิมจะถูก
เจือจางไปเรื่อยๆ ในบริบทที่ยาวขึ้น (goal drift / context dilution) ผลคือ
agent อาจ:
- ทำ task ย่อยเสร็จหมด แต่ผลรวมไม่ตรง goal จริง
- ประกาศ "เสร็จแล้ว" ทั้งที่ยังไม่ผ่านเงื่อนไขที่ตั้งไว้ (premature success)
- ค่อยๆ เปลี่ยน scope ไปตามสิ่งที่ทำได้ง่าย แทนที่จะยึดสิ่งที่ต้องทำจริง

หลักการแก้: **อย่าฝากเป้าหมายไว้ใน context/ความจำของ agent อย่างเดียว
ให้เขียนออกมาเป็นไฟล์ถาวร (durable artifact) แล้วบังคับให้กลับมาอ่าน/เช็ค
เป็นระยะ (re-anchoring)**

## ที่เก็บไฟล์ — โฟลเดอร์เดียว แยกจากไฟล์โปรเจกต์จริง
ไฟล์ทั้งหมดของ skill นี้อยู่ใต้ `.goal-keeper/` ที่ root ของงาน (ไม่ใช่ปนกับ
ไฟล์จริงของโปรเจกต์ที่ root เฉยๆ) เพื่อกันชนกับไฟล์ชื่อเดียวกันที่โปรเจกต์อาจมีอยู่แล้ว
และกันหลุดติด git commit ของ deliverable จริงโดยไม่ตั้งใจ:

```
.goal-keeper/
├── GOAL.md
├── PLAN.md
├── checkpoints/
│   ├── 001.md
│   ├── 002.md
│   └── ...
└── archive/                        # goal เก่าที่ปิดแล้ว ก่อนเปิด goal ใหม่ (ดูข้อ 0)
    └── <YYYY-MM-DD>-<slug>/
        ├── GOAL.md
        ├── PLAN.md
        └── checkpoints/
```

ถ้าอยู่ใน git repo และ `.goal-keeper/` ยังไม่อยู่ใน `.gitignore` ให้เพิ่มเข้าไป
(เว้นแต่ user ขอให้ commit ไฟล์พวกนี้เป็นส่วนหนึ่งของงานจริงๆ)

## ขั้นตอนการใช้งาน (บังคับทุกครั้ง)

### 0) ก่อนเริ่ม — นี่คือ "งานใหม่" จริงไหม หรือแค่ถามเฉยๆ
ไม่ใช่ทุกคำขอที่ต้องผ่าน goal-keeper:

- **คำถามอ่าน/อธิบาย/วิเคราะห์งานที่ทำเสร็จแล้ว** ("เจอบั๊กอะไรมั้ย", "ทำงานยังไง",
  "อธิบายโค้ดตรงนี้หน่อย", "มีอะไรต้อง improve/gap อีกมั้ย", "review ให้หน่อย")
  → **ข้าม goal-keeper ไปเลย** ตอบเป็น analysis ตรงๆ ไม่ต้องสร้างหรือแก้ไฟล์ใน
  `.goal-keeper/` ใดๆ ทั้งสิ้น (ไม่มี checkpoint ไม่มี GOAL.md ใหม่) แม้คำตอบจะ
  ชี้ gap หลายข้อก็ตาม — จะเข้า goal-keeper ก็ต่อเมื่อ user สั่งกลับมาให้ "แก้จริง"
  เท่านั้น ไม่ใช่ตอนที่แค่ระบุ gap ออกมา
- **งานใหม่ที่ต้องลงมือทำหลายขั้นตอนจริง** → เช็ค `.goal-keeper/GOAL.md` ก่อนเสมอ
  ถ้ายังไม่มีไฟล์ ให้ทำตามข้อ 1) ปกติ ถ้ามีไฟล์อยู่แล้ว:
  - ถ้า GOAL.md เดิมยังไม่ปิด (Definition of Done ยังไม่ผ่านครบ/ยังไม่ประกาศเสร็จ)
    และงานใหม่นี้คือ task ต่อเนื่องของ North Star เดิม → ทำงานต่อใน GOAL.md/PLAN.md
    เดิม อย่าสร้างใหม่ทับ
  - ถ้า GOAL.md เดิม**ปิดแล้ว** (ดูข้อ 4 ด้านล่าง) และงานใหม่นี้คือ North Star คนละอัน
    (เช่น "เพิ่ม feature 2" หลังจาก feature 1 เสร็จและปิดงานไปแล้ว) →
    **ห้ามแก้ทับ GOAL.md เดิม** ให้ย้าย `.goal-keeper/` ปัจจุบันทั้งโฟลเดอร์ไปเก็บที่
    `.goal-keeper/archive/<YYYY-MM-DD>-<slug เดิม>/` ก่อน แล้วค่อยสร้าง
    `.goal-keeper/GOAL.md` ใหม่สำหรับ North Star ใหม่ (feature 2 มี Definition of
    Done ของตัวเอง คนละชุดกับ feature 1)
  - ถ้าไม่แน่ใจว่าเป็นงานต่อเนื่องหรืองานใหม่ → ถามผู้ใช้สั้นๆ ก่อนตัดสินใจ

### 1) เริ่มงาน — เขียน Goal Brief ก่อนแตะ task ย่อยใดๆ
ก่อนเริ่มลงมือทำ ให้สร้างไฟล์ `.goal-keeper/GOAL.md` จาก template ที่
`templates/goal-brief.md` แล้วตอบให้ครบทุกช่อง โดยเฉพาะ:
- **North Star**: ผลลัพธ์สุดท้ายที่วัดได้ ไม่ใช่ activity ("ลูกค้าสมัครสมาชิกได้จริง
  ผ่านฟอร์ม" ไม่ใช่ "เขียนฟอร์มสมัครสมาชิก")
- **Definition of Done**: เกณฑ์ผ่าน/ไม่ผ่านที่ชัดเจน ตรวจสอบได้จริง (ไม่ใช่ความรู้สึก)
- **Non-goals**: สิ่งที่ห้ามทำ/ไม่ต้องทำ เพื่อกันการขยาย scope เอง
- **Constraints**: ข้อจำกัดที่ห้ามละเมิดไม่ว่ากรณีใด

ห้ามเริ่ม task ย่อยจนกว่า GOAL.md จะเขียนเสร็จและ (ถ้าเป็นไปได้) ให้ผู้ใช้ยืนยัน

### 2) แตก Goal เป็น Plan ที่อ้างอิงกลับหา Goal ได้เสมอ
สร้าง/อัปเดตไฟล์ `.goal-keeper/PLAN.md` (ใช้ template `templates/todo.md`) โดยแต่ละ
task ย่อยต้องมีคอลัมน์ **"เกี่ยวข้องกับ North Star ยังไง"** กำกับไว้เสมอ
ถ้าตอบคอลัมน์นี้ไม่ได้ = task นั้นน่าสงสัยว่ากำลังหลุด scope

### 3) ระหว่างทำงาน — Re-anchor ทุก N task หรือทุกครั้งก่อนตัดสินใจสำคัญ
ก่อนเริ่ม task ย่อยถัดไป **หรือ** เมื่อรู้สึกไม่แน่ใจ/ต้องตัดสินใจ fork ทาง
ให้ทำ "recitation" สั้นๆ แล้วบันทึกเป็น**ไฟล์ใหม่**ในโฟลเดอร์ `.goal-keeper/checkpoints/`
(คัดลอกจาก `templates/checkpoint-log.md`) — **ห้ามทับไฟล์เดิม** ตั้งชื่อไฟล์
เรียงเลขรัน เช่น `.goal-keeper/checkpoints/001.md`, `.goal-keeper/checkpoints/002.md`, ... เพื่อให้
ย้อนดู timeline การ re-anchor ทั้งหมดได้ ไม่ใช่เห็นแค่รอบล่าสุด **ก่อนสร้างไฟล์
ใหม่ทุกครั้ง ต้อง `ls .goal-keeper/checkpoints/` ก่อนเสมอ แล้วใช้เลขถัดจากไฟล์
ล่าสุด — ห้ามเดาเลขเอง** (ไม่งั้นเสี่ยงตั้งชื่อซ้ำแล้วทับของเดิมโดยไม่ตั้งใจ ซึ่งเป็น
ปัญหาเดียวกับที่โฟลเดอร์นี้มีไว้แก้):
1. อ่าน North Star + Definition of Done ใน `.goal-keeper/GOAL.md` ซ้ำ (อ่านจริง ไม่ใช่คิดเอาจากความจำ)
2. ถามตัวเอง: "สิ่งที่กำลังจะทำต่อไปนี้ push เข้าใกล้ North Star ขึ้นไหม หรือ
   แค่เป็นงานที่ทำง่าย/ถูกเรียกร้องเฉพาะหน้า?"
3. เช็ค progress เทียบ `.goal-keeper/PLAN.md` — มี task ไหนถูกข้าม/เบี่ยงไปโดยไม่ได้ตั้งใจไหม
4. ถ้าพบว่ากำลังเบี่ยง → หยุด, บันทึกเหตุผล, กลับไปที่ task ที่ตรง goal ก่อน

กติกา: **ห้าม** เก็บ goal ไว้แค่ใน context window อย่างเดียว — ทุกครั้งที่บริบท
ยาวขึ้นมาก (สรุป/compact) ต้องอ่าน .goal-keeper/GOAL.md ใหม่ทุกครั้งก่อนทำงานต่อ

### 4) ก่อนประกาศว่า "เสร็จ" — ผ่าน Verification Gate เท่านั้น
ห้ามบอกว่างานเสร็จจนกว่าจะเช็ค Definition of Done ใน `.goal-keeper/GOAL.md` ทีละข้อ
พร้อมหลักฐาน (test ผ่าน, ผลลัพธ์ตรวจสอบได้, output จริง ไม่ใช่ "น่าจะโอเค")
ถ้าข้อไหนไม่ผ่าน ห้ามปิดงาน ให้กลับไปแก้/เพิ่ม task ใหม่ใน `.goal-keeper/PLAN.md`

เมื่อผ่านครบทุกข้อและประกาศเสร็จจริง ให้ **มาร์กว่าปิดแล้ว**: เพิ่มบรรทัด
`## Status: CLOSED — <วันที่>` ต่อท้าย `.goal-keeper/GOAL.md` (เหนือ Changelog)
เพื่อให้รอบถัดไป (ดูข้อ 0) รู้ว่างานที่ตามมาต้องเปิด goal ใหม่ ไม่ใช่แก้ทับอันนี้

### 5) เมื่อ scope ต้องเปลี่ยนจริงๆ
ถ้าระหว่างทางพบว่า goal เดิมต้องปรับ (requirement เปลี่ยนจริง ไม่ใช่ agent
เบี่ยงเอง) ให้แก้ที่ `.goal-keeper/GOAL.md` อย่างเดียว (ใส่ log ว่าเปลี่ยนเพราะอะไร/เมื่อไหร่
ในตาราง Changelog ท้ายไฟล์) ห้ามแก้ scope เนียนๆ ผ่านการเปลี่ยน task ย่อยโดยไม่แตะ GOAL.md

## ทำงานร่วมกับ Skill อื่น (Orchestration Protocol)

`goal-keeper` **ไม่ใช่ skill ที่ทำงานจริง** (ไม่เขียนโค้ด ไม่ค้นข้อมูล ไม่สร้างเอกสารเอง)
หน้าที่ของมันคือเป็น **ชั้นควบคุมด้านบน** ที่คอยตัดสินว่าจะเรียก skill ไหน
เมื่อไหร่ และเช็คว่าผลลัพธ์ที่ได้กลับมายังพาไปสู่ North Star จริงไหม
ให้ยึดลำดับนี้เสมอเมื่อมี skill อื่นเกี่ยวข้อง:

### ก) ก่อนเรียก skill อื่นทุกครั้ง
1. เปิด `.goal-keeper/PLAN.md` หา task ย่อยที่กำลังจะทำ แล้วยืนยันว่ามันโยงกับ North Star
   ชัดเจน (ห้ามเรียก skill ไปทำ task ที่ตอบคอลัมน์นี้ไม่ได้)
2. สร้าง **Handoff Brief** สั้นๆ จาก template `templates/handoff-brief.md`
   แล้วแนบไปพร้อมกับคำสั่งเรียก skill นั้น — อย่าส่งแค่คำสั่งงานเปลือยๆ
   ("ทำ X ให้หน่อย") เพราะ skill ปลายทางจะไม่รู้ว่า X นี้อยู่ในภาพใหญ่ตรงไหน
   ต้องแนบ: North Star (สรุปสั้น), เกณฑ์ Definition of Done ข้อที่เกี่ยวกับ
   task นี้, Constraints/Non-goals ที่คุมอยู่, และรูปแบบ output ที่ต้องการ
3. สร้างไฟล์ checkpoint ใหม่ใน `.goal-keeper/checkpoints/` บันทึกว่า "กำลังจะเรียก skill ไหน
   ทำไม คาดหวังผลอะไร"

### ข) ระหว่าง/หลัง skill อื่นทำงานเสร็จ
1. **กรองผลลัพธ์เทียบ goal ก่อนรับเข้า context หลัก** — อย่าเอา output ดิบ
   ทั้งหมดจาก skill ที่ถูกเรียกไปยัดกลับเข้ามาทั้งก้อน ให้สรุปเฉพาะส่วนที่
   เกี่ยวกับ Definition of Done / North Star เท่านั้น ส่วนรายละเอียดดิบเก็บไว้
   เป็นไฟล์แยก อ้างอิงได้ภายหลังถ้าจำเป็น (กัน context ของ goal-keeper บวม
   จนเป้าหมายเจือจางไปเอง)
2. อัปเดตสถานะใน `.goal-keeper/PLAN.md` (⬜ → 🟨 → ✅) พร้อมอ้างอิงหลักฐานที่ได้จาก skill นั้น
   — ถ้า task ถูกปรับ/ตัดออกเพราะ re-anchor พบว่าหลงทาง ให้ใส่เลข checkpoint
   ที่ตัดสินใจนั้นไว้ในคอลัมน์ "อ้างอิง checkpoint" ด้วย ไม่ใช่แค่เปลี่ยนสถานะเฉยๆ
   (จะได้ตามรอยย้อนกลับไปดูเหตุผลได้จริง ไม่ใช่แค่เห็นผลลัพธ์ว่าเปลี่ยน)
3. ทำ **re-anchor** ตามขั้นตอนในหัวข้อ "ระหว่างทำงาน" ข้างบน ก่อนตัดสินใจว่า
   จะเรียก skill ตัวถัดไป, เรียกซ้ำ, หรือหยุด
4. ถ้าผลลัพธ์จาก skill นั้นไม่ตรงกับที่คาดไว้ใน Handoff Brief — ห้ามปล่อยผ่าน
   ให้บันทึกความคลาดเคลื่อนเป็นไฟล์ checkpoint ใหม่ใน `.goal-keeper/checkpoints/` แล้ว
   ตัดสินใจว่าจะเรียกซ้ำด้วย brief ที่ชัดขึ้น หรือปรับ `.goal-keeper/PLAN.md`

### ค) กติกาการอยู่ร่วมกับ skill อื่นใน session เดียวกัน
- `goal-keeper` โหลด/ทำงานตลอดทั้ง session ที่มี big goal ส่วน skill อื่น
  โหลดเฉพาะตอนถูกเรียกทำ task ย่อยแล้วจบไป — อย่าให้ skill งานเฉพาะ (เช่น
  coding skill, writing skill) เป็นคนตัดสินใจ scope หรือประกาศ "เสร็จทั้งงาน"
  เอง มีแค่ `goal-keeper` เท่านั้นที่เทียบกับ `.goal-keeper/GOAL.md` แล้วปิดงานได้
- ถ้า skill อื่นเสนอให้ขยายหรือเปลี่ยน scope กลางทาง (เช่น "เจอบั๊กเพิ่ม ควรทำ Y
  ด้วยไหม") ห้ามตอบรับทันที ให้เช็คกับ Non-goals/Constraints ใน `.goal-keeper/GOAL.md` ก่อน
  ถ้าจำเป็นจริงให้แก้ `.goal-keeper/GOAL.md` เป็นลายลักษณ์อักษร (ดูข้อ 5 ด้านบน) ไม่ใช่
  รับ scope ใหม่แบบเนียนๆ ผ่าน task ย่อย
- ถ้าหลาย skill dependent กัน (skill A ต้องเสร็จก่อน skill B ถึงเริ่มได้) ให้
  ระบุ dependency นี้ไว้ใน `.goal-keeper/PLAN.md` ไม่ใช่ปล่อยให้ agent ตัดสินใจเองตอนนั้น

## ไฟล์ที่ skill นี้ดูแล (durable state, อยู่นอก context)
- `.goal-keeper/GOAL.md` — เป้าหมายจริง, Definition of Done, Non-goals, Constraints
  (แก้ในไฟล์เดิมได้ แต่ต้อง log ลงตาราง Changelog ท้ายไฟล์ทุกครั้งที่ scope เปลี่ยนจริง)
