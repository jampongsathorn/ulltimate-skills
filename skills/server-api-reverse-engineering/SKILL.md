# Server/API Reverse Engineering (Black-box Web App)

Turn a browser action into a verified, reusable HTTP call by observing what an authorized web client already does. Modern web apps commonly pair a JavaScript frontend with server APIs; the goal is to recover that client-server contract from ground truth rather than inventing it.

This skill complements `agentic-problem-solving`: use its evidence loop when an experiment fails.

## Authorization and safety gate

Proceed only when the user owns the account/system or has explicit permission to automate it. Before testing:

- Prefer an official API, documented export, webhook, or supported integration if one meets the need.
- Keep scope to the exact user-authorized action and data.
- Never bypass CAPTCHA, fingerprinting, bot defenses, authorization checks, or rate limits. A security challenge is a stop signal: use an official route or a user-performed browser step.
- Never ask the user to paste cookies, tokens, or passwords into chat. Have them store exported credentials locally in an ignored secret file, or use an approved secret manager.
- Use test accounts and non-production targets where possible. Avoid mutation until a read-only session check succeeds.
- Do not collect unrelated endpoints, data, or credentials.

If authorization is uncertain, ask for confirmation before interacting with the target. Passive inspection of user-provided code is safer than active probing.

## Workflow

### 0. Establish an authorized session

The safest source of truth is browser DevTools **Network** while the user performs the action. Use “Copy as cURL” or export a sanitized HAR to capture the exact request. A HAR can contain secrets; keep it local, add it to `.gitignore`, and remove credentials before sharing or committing.

If a cookie jar is required, the user should export it after logging in through the normal flow and save it under the repository's ignored secret convention, such as `.sec/cookies.json` with restrictive permissions. Convert it to a request header at runtime—never embed it in source or logs.

First call a harmless identity/session endpoint observed in DevTools and verify the equivalent of `is_login: true`. If it fails, stop. Do not probe feature endpoints with an invalid session.

Typical local setup:

```bash
mkdir -p .sec
chmod 700 .sec
# Ensure .sec/ is ignored before placing any credentials there.
```

Use a browser-consistent `User-Agent`, `Referer`, and `Origin` only when the observed request requires them. Do not spoof headers to evade a control.

### 1. Capture the browser request first

Preferred order of evidence:

1. DevTools Network request generated by the exact button click.
2. Sanitized HAR or “Copy as cURL.”
3. Frontend source maps and unminified source.
4. Downloaded HTML and JavaScript bundles.
5. Validation-driven probing against an authorized test endpoint.

For the captured request, record:

- final URL, HTTP method, and redirect chain;
- query parameters and payload encoding;
- request headers, excluding incidental browser headers;
- CSRF token source and cookie relationship;
- response status, headers, and body;
- preflight or bootstrap requests required beforehand.

Redact `Cookie`, `Authorization`, CSRF values, signed URLs, account identifiers, and personal data in notes.

### 2. Discover bundles when traffic capture is insufficient

Download only publicly delivered assets for the authorized app:

```bash
curl -fsS --compressed "https://TARGET/" \
  -H "User-Agent: <browser UA>" \
  -o /tmp/target-page.html

grep -oE '(href|src)="[^"]*\.js[^" ]*"' /tmp/target-page.html
grep -oE 'href="?https://[^ >"]+\.js[^ >"]*' /tmp/target-page.html
```

Resolve relative URLs against the page origin instead of concatenating strings manually. Download into a temporary directory with bounded concurrency, timeout, size awareness, and failure reporting. Do not commit third-party bundles.

```bash
mkdir -p /tmp/target-js
# urls.txt must contain reviewed, same-app asset URLs only.
xargs -P 6 -n 1 curl -fsS --compressed --max-time 40 \
  --output-dir /tmp/target-js -O < urls.txt
```

Search for likely route and feature strings:

```bash
rg -o '"/(api|v1|v2|v3)[^"]{1,120}"' /tmp/target-js | sort -u
rg -i -n 'generate|custom[_-]?link|batch|conversion|csrf|sub_ids' /tmp/target-js
```

Treat discovered paths as leads, not proof. Record source file and surrounding context.

### 3. Find the caller, not just the endpoint

The caller reveals method, payload shape, preprocessing, and required headers. Inspect code around the route string and trace imports outward:

- Locate the module containing the request wrapper and identify its exported alias.
- Search for import/use sites of that alias across chunks.
- Search for distinctive payload keys such as `sub_ids`, not only the endpoint.
- Look for serializers, default values, array padding, and request interceptors.
- Inspect source maps when the server legitimately publishes them.

For minified module systems, note a module ID and trace where that ID is imported. Confirm every inferred field against either an observed request or server validation. Never assume a header is required merely because another endpoint uses it.

Common observed requirements include:

- CSRF header whose value corresponds to a CSRF cookie;
- `Content-Type` matching JSON or form encoding;
- `Origin`/`Referer` checks;
- `X-Requested-With: XMLHttpRequest` in older stacks;
- browser session cookies and an initialization request.

### 4. Build a minimal replay

Start from the captured request, then remove incidental fields one at a time. Test one item before a batch and use a read-only or dry-run route first where available.

```bash
curl --fail-with-body --silent --show-error \
  -X POST 'https://TARGET/api/observed-path' \
  -H 'Content-Type: application/json' \
  -H "X-CSRFToken: $CSRF_TOKEN" \
  -H "Cookie: $COOKIE_HEADER" \
  --data-binary @request.json
```

Keep secrets in environment variables or local ignored files. Disable shell tracing (`set +x`) before handling secrets, avoid verbose output, and never include real credential values in command history or reports.

Redirects require special care. `curl -L` may alter the method according to status and client behavior. First inspect the redirect without following it, then handle each allowed destination explicitly and preserve the method only when that matches the browser's observed behavior. Never forward credentials to a different origin.

### 5. Let errors narrow the contract

Read the complete status, headers, and response body. Change one field per attempt.

| Evidence | Meaning | Next action |
| --- | --- | --- |
| `401`, `403`, `is_login:false` | Session invalid or insufficient permission | Refresh via the normal login flow or obtain the required scope; do not bypass |
| `400`/`422`, field/property error | Authentication may have passed; payload contract is wrong | Minimize payload and correct one named field |
| `404`/`405` | Wrong route/version/method or deployment mismatch | Compare against captured traffic and live caller |
| `429` | Rate limit | Honor `Retry-After`, reduce volume, or use supported bulk APIs |
| `5xx`/timeout | Possibly transient or malformed edge case | Retry at most 1–2 times with backoff, then change evidence level |
| CAPTCHA, challenge, fingerprint error | Automation/security boundary | Stop direct replay; use official API or user-driven browser workflow |
| `2xx` but wrong data | Semantic or persistence failure | Verify identifiers, mapping, and downstream state |

An unchanged deterministic request should not be retried. Three different approaches means captured traffic, caller analysis, and a documented alternative—not three random payloads.

### 6. Verify independently

A success response is not sufficient. Verify through another route:

- Open a generated link and inspect the permitted redirect destination.
- Reload the UI and confirm persisted state.
- Read the created object through a separate GET endpoint.
- Compare one browser-generated result with one script-generated result.

Check both positive and negative cases. Test one record first, then a tiny batch, then the intended workload. Account for eventual consistency before declaring failure.

For affiliate links, confirm host allowlists, final product identity, attribution parameters, and that no secret query values are logged. Duplicate source products may legitimately produce the same result. Duplicate tracking IDs across products may destroy attribution quality, so validate uniqueness before sending when measurement depends on it.

### 7. Package the client

On the second successful replay, create a script under the repository's existing `scripts/` or `tools/` convention. It should:

- accept simple, documented inputs;
- load secrets from ignored files or environment variables;
- validate origin and reject credential forwarding across origins;
- set connect/read timeouts and bounded retries only for transient failures;
- respect `Retry-After` and use conservative pacing;
- offer dry-run mode for mutations;
- print actionable, redacted errors;
- return non-zero on partial batch failure;
- include an example and a focused test with mocked or sanitized fixtures.

Do not hard-code production hosts, cookies, CSRF tokens, account IDs, or a fixed one-second delay. Make pacing configurable and prefer server-provided limits.

## Example contract: Shopee Affiliate

The following is a historical, deployment-specific observation from Thailand in September 2026, not a guaranteed public contract. Reconfirm it from authorized live browser traffic before use:

```text
POST https://affiliate.shopee.co.th/api/v3/link/affiliate/batch/conversion
Content-Type: application/json

{"links":["<product_url>"],"sub_ids":["<sub1>","","","",""],"sub_client_channel":"website"}

Observed success shape:
{"code":0,"msg":"success","data":[{"original_url":"...","short_url":"https://s.shopee.co.th/XXX"}]}
```

Do not treat a historical endpoint as permission to call it, and do not attempt to work around a challenge response. Verify the resulting short link's destination and attribution before batching.

## Common traps checklist

- [ ] Redirect handling matches the browser; POST was not silently changed to GET.
- [ ] CSRF header and cookie relationship is reproduced without exposing values.
- [ ] A challenge on one endpoint was not generalized to all endpoints—and was not bypassed; an official alternative was sought.
- [ ] Cookies/tokens are short-lived, refreshable through the normal flow, and stored only in an ignored secret location.
- [ ] Duplicate inputs and duplicate outputs are handled intentionally.
- [ ] Tracking/sub IDs are unique where measurement requires uniqueness.
- [ ] Rate limits, terms, and approved automation scope are respected.
- [ ] Final state or redirect was independently verified.

## Closing checklist

- [ ] Confirmed ownership or explicit permission and checked for an official API first.
- [ ] Captured the exact browser request or documented why bundle analysis was needed.
- [ ] Kept cookies/tokens out of chat, source, logs, fixtures, and Git.
- [ ] Found the caller and verified method, payload, headers, and CSRF behavior.
- [ ] Replayed one minimal case with one-variable experiments.
- [ ] Stopped at CAPTCHA, bot-defense, authorization, and rate-limit boundaries.
- [ ] Verified the result independently before batching.
- [ ] Created a redaction-safe reusable tool with bounded retries and pacing.
- [ ] Recorded the endpoint contract, evidence date, constraints, and verification method.
